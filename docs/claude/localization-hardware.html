Sinhala Localization & Hardware

The two things that most often go wrong in Sri Lankan POS projects

1. Sinhala UI

  • i18n: i18next with si.json (default) and en.json; language switch in the header; every string keyed, no hard-coded text.
  • Fonts: bundle Noto Sans Sinhala (woff2) in the app; fallback Iskoola Pota (ships with Windows). Sinhala glyphs need ~10-15% more line height — use 1.5.
  • Unicode only, never legacy FM/DL fonts. Normalise to NFC before saving and before searching.
  • Input: on-screen keyboard component in the app (Sinhala Wijesekara/Singlish layout + English + numeric keypad), because Windows touch keyboard is awkward in kiosk mode. Physical keyboards: Windows Sinhala IME.
  • Search: FTS5 on Sinhala + a transliterated Singlish column (e.g. "සහල්" ⇄ "sahal"), prefix match.
  • Sorting: use Unicode collation (ICU) for Sinhala; keep a manual sort number for tiles.
  • Numbers/dates: Western digits and format 1,250.00, dates 2026-11-05, currency "රු." / "Rs."
  • Product names: store name_si and name_en; show Sinhala first, fallback English.
Test on the real machine in Phase 0: shaping of conjuncts (ක්‍ෂ, ශ්‍රී, ්‍ය) can break in some renderers. WebView2 (Chromium) handles them correctly; this is a reason to avoid older native widgets.

2. Touch UI rules (15.6" display)

  • Buttons ≥ 48×48 px (prefer 64 px for payment/keypad); 8-12 px gaps.
  • Main layout: left product grid / search, right bill panel, bottom action bar (Hold, Discount, Customer, Pay).
  • Big numeric keypad for qty and cash tendered with quick-cash buttons (500, 1000, 2000, 5000).
  • No hover-only UI; no small dropdowns — use full-screen pickers.
  • Disable text selection/pinch-zoom; confirm dialogs for destructive actions.

3. Receipt printing

  • Thermal printers have no Sinhala font ROM → render the receipt to a bitmap (HTML canvas or Rust image/ab_glyph with Noto Sinhala) at 203 dpi (58 mm = 384 px, 80 mm = 576 px width) and send as ESC/POS raster (GS v 0).
  • Transport: Windows spooler with RAW datatype to the installed printer name (works for USB and many drivers) or direct USB via rusb if drivers are problematic.
  • Print queue stored in print_job; auto retry; "Reprint last bill" button; printer-offline warning banner.
  • Receipt layout: shop name (si/en), address, phone, bill no, date/time, cashier, items (name, qty × price, total), subtotal, discount, total, paid, change, credit balance, footer, optional QR.
  • Raster printing is slower than text: keep header logo small and cut with GS V.

4. Cash drawer

  • Standard RJ11 drawer plugs into the printer; open with ESC/POS pulse ESC p 0 25 250 (pin 2) or ESC p 1 … (pin 5) depending on wiring — make pin configurable.
  • Kick only on cash payments, "No sale" (owner PIN), shift events; log each drawer open in audit.

5. Barcode scanner (phase 2)

  • USB scanners in HID keyboard-wedge mode: the app listens for fast keystroke bursts ending with Enter (< 50 ms between chars) on the POS screen — no driver needed.
  • Supports EAN-13, UPC, Code128; programmable prefix/suffix optional.
  • Unknown barcode → "Create product?" quick dialog (owner only).
  • Many local grocery items lack barcodes: allow shop-printed labels / quick-tap tiles for those.

6. Weighing scale (later)

Option A: price-embedded label barcodes (EAN-13 prefix 2, as printed by label scales) parsed by the app. Option B: RS-232/USB serial scale read in Rust. Decide after the shop confirms loose-goods volume.

7. Other hardware notes

  • Marcopos MP-TP001S: confirm available ports (USB count, COM, RJ11 drawer port) — some models have an internal built-in printer; check whether it includes one (the "TP" may indicate thermal printer). Update memorry.md after checking.
  • Recommend a small UPS (power cuts) and a spare USB thermal printer.
  • Turn off Windows sleep/hibernate; set power plan to High performance; keep SSD > 20% free.
