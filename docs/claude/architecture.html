4. Sale flow (critical path)

Scan/tap items → cart (memory) → Pay
  BEGIN TRANSACTION (SQLite)
    insert sale + sale_items + payments
    insert stock_movements (negative)
    update customer credit ledger (if credit)
    insert audit_log, outbox rows, print_job
  COMMIT                         ← sale is now durable
→ print receipt (async) + kick drawer → UI shows "done"
→ sync worker later pushes outbox rows to Supabase

5. Sync design

  • Direction (v1): device → cloud only. The shop PC is the master for its own data, so no conflict resolution is needed. Cloud → device only for config (prices pushed from owner later).
  • Outbox pattern: table outbox(id, table, row_id, op, payload, created_at, sent_at, attempts); worker batches 100 rows, POSTs via Supabase REST/RPC with device JWT, marks sent on 2xx, exponential backoff.
  • Idempotent: UUID v7 primary keys + upsert on conflict (id); replays are safe.
  • Ordering: per-table sequence device_seq to detect gaps.
  • Connectivity: health check every 60 s; sync only on success; never blocks UI.
  • Backups: daily 'VACUUM INTO' snapshot → zip → AES-256 → local folder + Supabase Storage (keep 30 days).

7. Key technology notes

  • Tauri 2 needs WebView2 (included in Win10 21H2+ updates; installer ships the bootstrapper).
  • SQLite in WAL mode, synchronous=FULL for sale commits (power-cut safety).
  • Money as INTEGER cents; rounding rule defined once in Rust.
  • Updates: Tauri updater with signed releases from GitHub; manual approve by owner.
  • Logging: rotating log file in %APPDATA%\TavrionPOS\logs, no personal data.
  • Remote support: optional AnyDesk/RustDesk installed separately.
